# AGENTS.md

## Назначение режима

Этот файл переводит Codex в режим **работы только с документацией**.

Основная задача агента:

- изучать существующий код и конфигурацию проекта;
- сопоставлять фактическое состояние проекта с документацией;
- создавать, уточнять и редактировать документацию;
- не изменять исходный код, конфигурацию, зависимости и другие файлы реализации.

## Жёсткое ограничение на изменения

Агенту разрешено изменять только документационные файлы в формате Markdown:

```text
*.md
```

В первую очередь это относится к документации frontend, расположенной в `docs/` или другой существующей папке документации проекта.

Не изменять сам `AGENTS.md`, если пользователь явно не попросил об этом.

## Что разрешено

Агент может:

- читать любые файлы репозитория;
- анализировать frontend- и backend-код;
- проверять фактическую структуру проекта;
- читать `package.json`, lock-файлы и конфигурационные файлы;
- проверять версии и наличие зависимостей;
- искать использование библиотек, компонентов, API и архитектурных решений;
- сравнивать реализацию с документацией;
- редактировать существующие Markdown-документы;
- создавать новые Markdown-документы, если они действительно необходимы для текущей задачи;
- исправлять противоречия, дублирование, устаревшие формулировки и структуру документации;
- добавлять в документацию замечания о расхождениях между целевой архитектурой и текущим кодом.

Чтение кода используется только как источник информации. Наличие проблемы в коде не даёт права исправлять её.

```text

*.jsx

```

Также запрещено:

- добавлять, удалять или обновлять зависимости;
- запускать установку пакетов;
- изменять lock-файлы;
- создавать компоненты, hooks, API-клиенты, маршруты, модели или утилиты;
- исправлять найденные ошибки в коде;
- выполнять рефакторинг;
- менять форматирование исходного кода;
- запускать команды, которые могут автоматически изменить файлы;
- выполнять генерацию кода;
- применять миграции;
- менять переменные окружения;
- делать изменения «заодно», даже если они кажутся полезными.

Если для выполнения документационной задачи требуется изменение кода или конфигурации, агент должен только описать это как отдельное последующее действие.

Не запускать команды с автоматическим исправлением или генерацией файлов.


Если обнаружены изменения в коде, которые существовали до начала работы, не откатывать и не редактировать их. В итоговом сообщении явно отметить, что эти изменения не принадлежат агенту.

## Текущая документационная задача

Нужно актуализировать frontend-документацию после принятия нового решения по стилизации приложения.

### Зафиксированное решение

Основная UI-библиотека:

```text
Mantine
```

Для стилизации использовать:

```text
Mantine theme
CSS Modules
postcss-preset-mantine
postcss-simple-vars
Motion
```

Для иконок:

```text
@tabler/icons-react
```

Tailwind CSS не входит в целевой frontend-стек и не должен упоминаться как обязательная или рекомендуемая технология проекта.

### Распределение ответственности за стили

Документация должна закреплять следующие правила.

#### Mantine theme

Используется для глобальной дизайн-системы:

- цветовой палитры;
- основной темы приложения;
- типографики;
- радиусов;
- теней;
- breakpoints;
- глобальных параметров компонентов;
- согласованного оформления светлой и тёмной тем.

#### Mantine-компоненты и style props

Используются для простого layout и композиции:

- `Stack`;
- `Group`;
- `Flex`;
- `Grid`;
- spacing;
- размеры;
- alignment;
- простые responsive-настройки.

Не создавать CSS-класс только ради элементарного layout, который ясно выражается средствами Mantine.

#### CSS Modules

Используются для собственного визуального оформления компонентов:

- сложных фонов и градиентов;
- нестандартной сетки;
- декоративных элементов;
- сложного позиционирования;
- адаптивных правил компонента;
- hover, active, focus и других состояний;
- оформления внутренних частей Mantine-компонентов через `classNames` и Styles API;
- отдельных правил для светлой и тёмной темы.

CSS Module должен находиться рядом с компонентом, которому принадлежит.

Пример структуры:

```text
savings-summary/
├── savings-summary.tsx
└── savings-summary.module.css
```

#### Глобальные стили

Глобальный CSS должен оставаться минимальным и использоваться только для действительно глобальных правил:

- `html`;
- `body`;
- `#root`;
- базового фона;
- минимальной высоты приложения;
- глобального сглаживания шрифтов;
- редких общих reset-правил.

Не переносить компонентные стили в глобальный CSS.

#### Motion

Используется для поведенческих и составных анимаций:

- анимации изменения накопленной суммы;
- появления и удаления элементов;
- layout transitions;
- переходов между состояниями;
- анимации карточек и progress-блоков.

Простые изменения цвета, opacity, border и hover-состояния реализуются CSS transitions.

### Темы

Приложение должно поддерживать ровно две пользовательские темы:

```text
light
dark
```

Обе темы строятся через Mantine theme и CSS variables.

CSS Modules не должны содержать хаотично продублированные цвета. Для цветов, отступов, радиусов и других повторяющихся значений следует использовать design tokens и CSS variables Mantine.

### Что необходимо обновить в документации

Найти существующие frontend-документы. Ожидаемые документы могут называться примерно так:

```text
01-FRONTEND_BUSINESS_SPEC.md
02-FRONTEND_ARCHITECTURE.md
03-FRONTEND_TECHNICAL_SPEC.md
04-FRONTEND_IMPLEMENTATION_PLAN.md
```

Фактические пути и имена определить по репозиторию.

Проверить и при необходимости обновить:

1. Перечень frontend-технологий.
2. Раздел об архитектуре UI и стилей.
3. Правила размещения CSS Modules.
4. Разделение ответственности Mantine theme, Mantine props, CSS Modules и Motion.
5. Требования к светлой и тёмной темам.
6. Перечень обязательных пакетов.
7. Этап настройки PostCSS в плане реализации.
8. Этап создания темы и глобальных design tokens.
9. Этап стилизации feature-компонентов.
10. Критерии приёмки по отсутствию Tailwind в целевом стеке.

Удалить или переписать устаревшие положения, в которых Tailwind:

- указан как обязательная зависимость;
- используется как основной способ layout;
- предлагается для компонентных стилей;
- включён в этапы установки и конфигурации;
- фигурирует в Definition of Done.

Не удалять слово `Tailwind`, если оно используется в историческом пояснении или в явной формулировке, что библиотека не применяется. Такие упоминания должны быть редкими и однозначными.

## Границы текущей задачи

Не менять без необходимости другие ранее согласованные решения:

- React;
- TypeScript;
- Vite;
- pnpm;
- TanStack Router;
- TanStack Query;
- session-based авторизацию через HttpOnly cookie;
- frontend-расчёты финансовых агрегатов;
- feature-oriented архитектуру;
- отсутствие обязательного global state manager;
- условное подключение TanStack Form и TanStack Table;
- PWA;
- отсутствие автоматических frontend-тестов в текущем MVP.

Не расширять задачу на переработку бизнес-требований, API-контракта или backend-документации, если для согласованности стилистического решения это не требуется.

## Порядок работы

### 1. Изучить репозиторий

- прочитать корневой `AGENTS.md`;
- найти frontend-документацию;
- изучить связанные Markdown-файлы;
- проверить текущие frontend-зависимости и конфигурацию только для понимания фактического состояния;
- найти все содержательные упоминания Tailwind, CSS Modules, Mantine, PostCSS и Motion.

### 2. Составить краткий план

До редактирования перечислить:

- какие Markdown-файлы будут изменены;
- какие противоречия обнаружены;
- какие разделы требуют синхронизации.

Не предлагать изменения кода в качестве части текущего выполнения.

### 3. Обновить документацию

- сохранить существующую структуру документов, если она остаётся понятной;
- не переписывать документы целиком без необходимости;
- использовать единые термины во всех файлах;
- различать текущее состояние репозитория и целевое состояние, если они ещё не совпадают;
- не утверждать, что техническая миграция уже выполнена, если изменена только документация.

### 4. Проверить согласованность

После редактирования проверить:

- совпадает ли стек во всех документах;
- исключён ли Tailwind из обязательных зависимостей;
- присутствуют ли CSS Modules и PostCSS;
- одинаково ли описано распределение ответственности за стили;
- не осталось ли взаимоисключающих требований;
- не изменены ли файлы реализации.

### 5. Проверить diff

Обязательно выполнить:

```text
git diff --name-only
git diff --check
git diff
```

Убедиться, что агент изменил только Markdown-файлы.

## Формат итогового ответа

В завершении кратко указать:

1. Какие документы изменены.
2. Какие архитектурные решения зафиксированы.
3. Какие противоречия устранены.
4. Были ли обнаружены расхождения между документацией и текущим кодом.
5. Что код, конфигурация и зависимости не изменялись.

Не заявлять о выполнении технической миграции. Результат текущей задачи — только обновлённая документация.
