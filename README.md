# Квартирка

Локальное приложение для общих накоплений и покупок: React, TypeScript, Vite, Mantine, TanStack Router и TanStack Query. Интерфейс на русском языке, со светлой и тёмной темами и мобильной навигацией.

Реализованы вход через session cookie, цель и история накоплений, месячный план, покупки с фильтрами и статусами, профиль и выход. Данные хранятся в настоящем PostgreSQL через соседний NestJS backend.

## Запуск в подготовленном окружении

Требуются Node.js 24, Docker Desktop и pnpm. В обоих repository закреплён pnpm 10.34.5. Команды нужно выполнять из соответствующего repository.

1. В `KvartirkaBackend` запустить PostgreSQL и backend:

    ```powershell
    docker compose up -d postgres
    pnpm dev
    ```

2. В другом терминале, в `KvartirkaFrontend`:

    ```powershell
    pnpm dev
    ```

3. Открыть [Квартирку](http://localhost:5173). Для входа используются существующие аккаунты backend. Отсутствие цели после входа — нормальное начальное состояние: нажмите «Создать цель».

Backend по умолчанию слушает порт 3000. [Проверка состояния backend](http://localhost:3000/health) должна возвращать HTTP 200. Vite слушает только loopback и использует фиксированный порт 5173; если порт занят, он сообщает об ошибке, а не запускается на другом origin.

## Открытие со смартфона в локальной сети

Телефон должен быть подключён к Wi-Fi того же роутера, к которому подключён компьютер. Компьютер может использовать Ethernet.

При работающем backend вместо обычного frontend dev server запустить `pnpm dev:lan`. Эта команда включает прослушивание сетевых интерфейсов через поддерживаемый Vite параметр [`--host`](https://vite.dev/config/server-options.html#server-host); обычный `pnpm dev` по-прежнему доступен только на компьютере.

На телефоне открыть `http://<IPv4 компьютера>:5173`. На момент настройки адрес — [http://192.168.1.169:5173](http://192.168.1.169:5173); после смены сети или выдачи нового DHCP-адреса он может измениться. `localhost` на телефоне обозначает сам телефон. Вход нужно выполнить отдельно: cookie браузера компьютера на телефон не переносится.

API остаётся относительным `/api/v1` и проходит через Vite proxy. Открывать порт backend на телефоне и менять `APP_ORIGIN` для этого сценария не требуется. Компьютер, backend и frontend должны продолжать работать.

Если адрес не открывается, проверить, что телефон находится в той же локальной сети, Wi-Fi не гостевой и не включает изоляцию клиентов, а firewall допускает входящий TCP 5173 из домашней подсети. Для возврата к обычному режиму остановить `dev:lan` и запустить `pnpm dev`.

Этот запуск позволяет проверить интерфейс в мобильном браузере. Service worker включается в production build; для полноценной PWA-проверки на iPhone нужен HTTPS-адрес этой сборки. Обычный HTTP-адрес компьютера в локальной сети для этого не подходит.

## Первоначальная подготовка

Если зависимости ещё не установлены, выполнить `pnpm install --frozen-lockfile` в каждом repository. Backend требует свою `.env`, созданную по его `.env.example`.

Основные настройки backend:

| Переменная                       | Назначение                                                               |
| -------------------------------- | ------------------------------------------------------------------------ |
| `NODE_ENV`                       | `development` для локального запуска                                     |
| `PORT`                           | Порт API, обычно `3000`                                                  |
| `DATABASE_URL`                   | Подключение к локальной БД; порт должен совпадать с пробросом PostgreSQL |
| `APP_ORIGIN`                     | `http://localhost:5173`                                                  |
| `COOKIE_SECURE`                  | `false` для локального HTTP                                              |
| `SESSION_TTL_DAYS`               | Срок жизни сессии по конфигурации backend                                |
| `POSTGRES_PORT`                  | При необходимости свободный порт хоста для Docker Compose                |
| `SEED_USER_1_*`, `SEED_USER_2_*` | Данные двух пользователей при первоначальном seed                        |

После запуска PostgreSQL в backend выполнить `pnpm prisma:generate` и `pnpm prisma:migrate:deploy`. Для новой пустой БД заполнить seed-переменные и выполнить `pnpm prisma:seed`. Повторный seed обновляет пользователей и может обновить цель; для обычного запуска уже подготовленной БД он не нужен.

Во frontend секреты не задаются. Необязательная `.env` по примеру `.env.example` содержит только `API_PROXY_TARGET`. Этот адрес использует Vite для dev/preview proxy; в клиентском bundle всегда остаётся относительный `/api/v1`.

## Проверки и собранная версия

Из frontend repository:

```powershell
pnpm lint
pnpm typecheck
pnpm format:check
pnpm build
```

Все проверки вместе: `pnpm check`.

После сборки выполнить `pnpm preview` и открыть [production-preview](http://localhost:4173). Backend должен продолжать работать: preview также проксирует `/api` по `API_PROXY_TARGET`. Preview предназначен для локальной проверки сборки; публикация потребует отдельного web server с SPA fallback и reverse proxy API.

Файл `src/routeTree.gen.ts` создаёт TanStack Router plugin; он хранится вместе с исходниками и не редактируется вручную. После добавления route-файлов запускайте dev server для актуализации дерева перед отдельным typecheck.

## PWA на iPhone

Целевая ручная проверка: iPhone 17, iOS 26.6.2, Safari и запуск с домашнего экрана. Код PWA добавлен; проверка реального устройства остаётся за пользователем.

Для установки открыть HTTPS-адрес production-сборки в Safari, выбрать «Поделиться» → «На экран Домой» и включить открытие как веб-приложения, если этот переключатель показан. Затем запустить «Квартирку» с появившейся иконки. API должен оставаться доступным по `/api/v1` на том же origin.

Service worker сохраняет оболочку, JS/CSS и иконки. Приватные API-ответы и сохранения не кешируются. После предварительного онлайн-запуска оболочка может открываться без сети, но для входа, загрузки данных и изменений нужен backend. Уже открытая страница может показывать данные из памяти; они не становятся постоянной offline-копией.

При новой версии появляется предложение обновиться. «Позже» откладывает его до следующего возвращения к приложению или запуска. «Обновить» открывает подтверждение перезагрузки с предупреждением о несохранённых полях. Пока выполняется mutation, обновление недоступно. Если открыты другие вкладки этого же приложения, перед активацией потребуется закрыть их. Проверка новой версии выполняется при возвращении к приложению, восстановлении сети и раз в час в видимом окне.

При размещении сборки web server должен отдавать SPA fallback для UI-маршрутов, проксировать API отдельно и не подменять отсутствующие JS/CSS, manifest или SW файлом index.html. Для index.html, sw.js, pwa-update.js и manifest.webmanifest нужна перепроверка актуальности без длительного immutable-кеша; хешированные assets могут кешироваться надолго. Production deployment и HTTPS-стенд в этой задаче не настраивались.

Пошаговые действия и ожидаемые результаты: [ручной чек-лист iPhone](docs/09-PWA_MVP_VERIFICATION.md). Приёмку нельзя считать пройденной только по наличию иконки на домашнем экране.

## Поведение и ограничения первой версии

- Исходные данные принадлежат backend; сводки вычисляются на frontend. Денежные значения API — целые копейки. Суммирование и округление плана используют `bigint`, чтобы не терять копейки при больших общих суммах.
- Месячный план опирается на остаток на начало месяца. Текущие пополнения уменьшают остаток месяца; прошлые записи изменяют сам план. Смена дня/месяца учитывается без перезагрузки страницы.
- Фильтры покупок хранятся в URL. Финансовая сводка всегда относится ко всему списку. Нулевая цена означает «Цена не указана».
- После входа, выхода и истечения сессии загружается новый документ. Это изолирует кеш и незавершённые callbacks между сессиями. Cookie недоступна JavaScript.
- При ошибке сохранения форма остаётся открытой. Автоматической повторной отправки и offline-очереди mutations нет.
- Данные второго пользователя обновляются при возвращении фокуса в окно, восстановлении подключения или ручном обновлении. Постоянной real-time синхронизации нет.
- PWA включает кеш оболочки и управляемые обновления. Offline-редактирование, публичный deployment и собственная дизайн-система остаются за границами этой версии.
- Автоматические браузерные тесты не добавлялись по уточнённому решению пользователя. Статические проверки и непройденные вручную сценарии разделены в отчёте PWA.
