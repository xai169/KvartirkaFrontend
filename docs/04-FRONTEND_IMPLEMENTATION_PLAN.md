# Подробный план реализации frontend приложения «Квартирка»

## 1. Назначение документа

Документ задаёт последовательный pipeline реализации frontend: от проверки repository и настройки базового каркаса до готового MVP, интегрированного с существующим backend.

План должен использоваться вместе с:

- `01-FRONTEND_BUSINESS_SPEC.md` — бизнес-поведение приложения;
- `02-FRONTEND_ARCHITECTURE.md` — структура проекта и правила зависимостей;
- `03-FRONTEND_TECHNICAL_SPEC.md` — технические требования;
- `05-FRONTEND_EXECUTION_CHECKLIST.md` — компактный рабочий маршрут по этапам разработки;
- backend-ТЗ — фактический HTTP-контракт и ограничения серверной части.

Этот документ отвечает прежде всего на вопросы:

- в каком порядке реализовывать части приложения;
- какие зависимости должны быть готовы перед каждым этапом;
- какие файлы и модули необходимо создать;
- что должно работать после завершения этапа;
- какие ручные проверки нужно выполнить;
- что нельзя добавлять преждевременно.

План не требует реализовывать весь frontend одним большим изменением. После каждого этапа приложение должно оставаться запускаемым и находиться в состоянии, на которое можно безопасно опереться в следующем этапе.

Для ежедневной работы использовать `05-FRONTEND_EXECUTION_CHECKLIST.md`: он показывает текущий этап, последовательность действий, ожидаемый результат и короткую проверку. Этот документ остаётся подробным справочником для случаев, когда рабочего плана недостаточно.

# 2. Зафиксированные решения

Перед началом разработки считать утверждёнными следующие решения.

## 2.1. Архитектура

Используется облегчённая feature-oriented архитектура без полного FSD.

Основные области исходного кода:

- `app` — глобальная инициализация приложения;
- `routes` — TanStack Router и route-level логика;
- `pages` — композиция экранов;
- `features` — предметные области `auth`, `savings`, `purchases`, `profile`;
- `shared` — действительно общая инфраструктура, UI и утилиты.

Внутри feature допускаются папки:

- `api`;
- `model`;
- `ui`.

Не создавать глобальные каталоги `components`, `types`, `services` и `utils`, в которые складывается несвязанный код из разных предметных областей.

## 2.2. Backend и расчёты

Backend является persistence API и возвращает исходные данные.

Frontend самостоятельно рассчитывает:

- текущую сумму накоплений;
- остаток до цели;
- процент выполнения;
- месячный план;
- выполнение плана текущего месяца;
- суммы покупок по статусам;
- количество покупок без цены;
- группировки, фильтры и сортировку.

Производные значения не сохраняются в React state, TanStack Query cache как отдельные серверные сущности или backend.

## 2.3. API и авторизация

Frontend обращается к относительному base path `/api/v1`.

В development Vite proxy перенаправляет `/api` на локальный NestJS backend. В production Nginx должен отдавать frontend и проксировать `/api/v1` на backend под одним origin.

Авторизация основана на server-side session:

- frontend не получает и не хранит access token;
- frontend не получает и не хранит refresh token;
- session token находится в HttpOnly cookie;
- все API-запросы отправляются с cookie credentials;
- источником истины авторизации является `GET /api/v1/me`.

## 2.4. Формы и validation

На старте не устанавливать Zod только ради API-запросов или небольших форм.

Использовать:

- локальное React state;
- небольшие feature-level функции проверки полей;
- типизированные request DTO;
- mapping значений формы в API input при необходимости.

Zod допускается добавить позднее, если правила валидации становятся разветвлёнными и ручная реализация начинает дублироваться.

TanStack Form подключается только при появлении действительно сложных форм: зависимых полей, nested values, массивов, сложного dirty-state или повторяемого field lifecycle.

## 2.5. Стили, темы и язык

Основная UI-библиотека — Mantine.

Распределение ответственности:

- Mantine theme хранит глобальную палитру, typography, radius, shadows, breakpoints, component defaults и light/dark tokens;
- Mantine layout-компоненты и style props выражают простую композицию, spacing, размеры и alignment;
- colocated CSS Modules отвечают за собственное визуальное оформление, сложное позиционирование, component-level responsive rules и состояния;
- `classNames` и Styles API применяются для оформления внутренних частей Mantine-компонентов;
- глобальный CSS содержит только правила уровня `html`, `body`, `#root` и общий visual baseline;
- Motion используется для enter/exit, layout transitions и поведенческих анимаций, а простые hover/color/opacity transitions остаются в CSS.

CSS обрабатывается PostCSS с `postcss-preset-mantine` и `postcss-simple-vars`. Tailwind CSS в целевой стек не входит.

Интерфейс поддерживает ровно две темы:

- светлую;
- тёмную.

Выбор темы хранится локально в браузере.

Интерфейс только русский. Мультиязычность и i18n-библиотеки в MVP не входят.

## 2.6. Тесты

Автоматические frontend-тесты в текущий MVP не входят.

Качество проверяется через:

- TypeScript;
- ESLint;
- Prettier;
- production build;
- ручные сценарии после каждого этапа;
- финальную интеграционную приёмку.

Чистые функции расчётов должны быть спроектированы так, чтобы позднее их можно было покрыть unit-тестами без изменения архитектуры.

# 3. Общий порядок работы

## 3.1. Перед каждым этапом

Перед реализацией очередного этапа необходимо:

1. Изучить текущее состояние repository.
2. Проверить незакоммиченные изменения и не затереть работу пользователя.
3. Сопоставить этап с актуальными frontend- и backend-документами.
4. Определить, какие части этапа уже реализованы.
5. Составить короткий план конкретных изменений.
6. Не добавлять функциональность следующих этапов «заодно».
7. Не устанавливать библиотеки, необходимость которых пока не возникла.

## 3.2. После каждого этапа

После реализации необходимо:

1. Запустить доступные quality-команды.
2. Запустить production build.
3. Открыть приложение вручную.
4. Пройти ручные сценарии этапа.
5. Проверить browser console.
6. Проверить network requests, если этап связан с API.
7. Просмотреть `git diff`.
8. Удалить временные debug-элементы и логи.
9. Убедиться, что в commit не попали `.env`, secrets и несвязанные файлы.
10. Сделать отдельный commit с коротким сообщением на русском.

Минимальный набор проверок после появления соответствующих scripts:

- `pnpm lint`;
- `pnpm typecheck`;
- `pnpm format:check`;
- `pnpm build`.

## 3.3. Критерий завершения этапа

Этап считается завершённым, только если:

- заявленный результат работает, а не существует в виде пустых файлов;
- приложение запускается;
- TypeScript и build не содержат blocking errors;
- временные заглушки либо удалены, либо явно относятся к будущему этапу;
- следующий этап может использовать созданный код без предварительной переделки;
- архитектурные границы не нарушены ради ускорения реализации.

# 4. Сводный pipeline

Рекомендуемая последовательность:

1. Preflight и синхронизация контрактов.
2. Инициализация React/Vite/TypeScript/pnpm.
3. Установка обязательных пакетов и настройка tooling.
4. Создание архитектурного каркаса.
5. Настройка Mantine theme, CSS Modules, PostCSS и двух тем.
6. Настройка TanStack Router и базовых страниц.
7. Реализация адаптивного AppShell и навигации.
8. Реализация общего API client и TanStack Query.
9. Реализация session-based авторизации.
10. Создание общих primitives для денег, дат и ошибок.
11. Реализация модели, API и расчётов накоплений.
12. Реализация экрана накоплений и CRUD.
13. Реализация модели, API и расчётов покупок.
14. Реализация экрана покупок, фильтров и CRUD.
15. Реализация профиля, переключения темы и logout.
16. Унификация loading/error/empty состояний, accessibility и анимаций.
17. Настройка PWA.
18. Финальная интеграционная приёмка.
19. Подготовка frontend к будущей публикации на VPS.

Разделы накоплений и покупок реализуются вертикально: сначала модель и API конкретной feature, затем пользовательский экран этой feature. Не следует сначала писать весь API-слой приложения, затем все модели и только после этого все страницы.

# 5. Этап 0. Preflight и синхронизация контрактов

## Цель

Понять фактическое состояние repository и убрать неопределённость до появления production-кода.

## Предварительные условия

- доступен repository;
- доступно актуальное backend-ТЗ;
- известно, где находится или будет находиться frontend;
- backend уже реализуется либо его контракт зафиксирован.

## Действия

### 5.1. Изучить repository

1. Определить, является ли repository монорепозиторием или отдельным backend-проектом.
2. Найти существующие `package.json`, workspace-конфигурацию и lockfile.
3. Проверить наличие готового frontend-каталога.
4. Проверить существующие правила именования файлов и каталогов.
5. Проверить наличие `AGENTS.md`, README и repository-level инструкций.
6. Проверить Git status и текущую ветку.

### 5.2. Проверить версии инструментов

Зафиксировать:

- Node.js 24 LTS;
- используемую версию pnpm;
- TypeScript;
- Vite;
- React;
- ограничения существующего CI, если он уже есть.

Не обновлять backend-зависимости в рамках frontend-задачи без необходимости.

### 5.3. Сверить API-контракт

Проверить наличие и фактическую форму endpoints:

- `POST /api/v1/auth/login`;
- `POST /api/v1/auth/logout`;
- `GET /api/v1/me`;
- `GET` и `PUT /api/v1/savings/goal`;
- CRUD `/api/v1/savings/entries`;
- CRUD `/api/v1/purchases`;
- `GET /health`.

Отдельно подтвердить:

- авторизация через HttpOnly cookie;
- имя cookie frontend не требуется знать;
- cookie в development создаётся без `Secure`;
- POST, PUT и PATCH возвращают актуальную сущность;
- DELETE возвращает `204` без body;
- ошибки соответствуют единому backend-контракту;
- деньги передаются в integer minor units;
- даты без времени передаются в `YYYY-MM-DD`;
- timestamps передаются в ISO 8601 UTC.

### 5.4. Зафиксировать локальную схему запуска

Целевая dev-схема:

- Vite frontend на стандартном frontend-порту;
- NestJS backend на локальном backend-порту;
- frontend обращается только к `/api/v1`;
- Vite proxy перенаправляет `/api` на backend;
- PostgreSQL запускается согласно backend-инструкции.

Не использовать hardcoded абсолютный backend URL в feature-коде.

### 5.5. Проверить границы MVP

Подтвердить, что сейчас не реализуются:

- регистрация;
- редактирование профиля;
- аватар;
- графики;
- i18n;
- custom rooms/categories;
- поиск;
- pagination;
- offline mutations;
- frontend-тесты;
- TanStack Form;
- TanStack Table;
- отдельный state manager.

## Результат этапа

- понятна целевая директория frontend;
- понятен локальный запуск;
- frontend-решения не противоречат backend;
- нет необходимости переделывать контракт посреди инициализации.

## Ручная проверка

- backend запускается либо его контракт однозначно доступен;
- `/health` отвечает согласно backend-ТЗ;
- нет конфликтующего frontend-каркаса;
- выбран один package manager и один lockfile.

## Критерий готовности к следующему этапу

Можно точно указать, где будет создан frontend, как он будет запускаться и по какому адресу обращаться к API.

## Рекомендуемый commit

Если код не менялся, commit не нужен. Если добавлена или актуализирована только документация: `Актуализирована документация frontend`.

# 6. Этап 1. Инициализация React/Vite/TypeScript/pnpm

## Цель

Получить минимальное, чистое и запускаемое React-приложение без предметной функциональности.

## Зависимости

Завершён этап 0.

## Действия

### 6.1. Создать приложение

1. Инициализировать Vite-проект с React и TypeScript в утверждённой директории.
2. Использовать pnpm и существующую workspace-схему, если repository уже является монорепозиторием.
3. Не создавать второй lockfile и не использовать npm/yarn.
4. Проверить корректность package name и отсутствие случайных demo-названий.

### 6.2. Очистить стартовый шаблон

1. Удалить Vite logo, demo assets и демонстрационные стили.
2. Удалить счётчик и примерный UI.
3. Оставить минимальную точку входа и application root.
4. Не добавлять временную бизнес-разметку, которая будет удалена через один этап.

### 6.3. Настроить TypeScript

1. Включить strict mode.
2. Не разрешать `any` как обычный способ обхода типизации.
3. Разделить browser и tooling types, если конфигурация Vite этого требует.
4. Настроить alias `@` на `src`, если он не конфликтует с текущим repository.
5. Проверить, что alias одинаково понимают TypeScript и Vite.

### 6.4. Настроить базовые scripts

Добавить scripts для:

- development server;
- production build;
- production preview;
- отдельной проверки TypeScript.

Lint и formatting scripts добавляются на следующем этапе.

### 6.5. Настроить базовые repository-файлы

1. Проверить `.gitignore`.
2. Исключить `dist`, локальные env-файлы и Vite cache.
3. Не добавлять `VITE_API_BASE_URL`, так как приложение использует относительный `/api/v1`.
4. Добавить frontend README только если repository требует отдельной инструкции запуска.
5. Зафиксировать Node/pnpm version существующим в repository способом.

## Результат этапа

- приложение открывается в браузере;
- demo-код удалён;
- TypeScript strict включён;
- production build создаётся;
- структура пока минимальна и не содержит преждевременных abstraction.

## Ручная проверка

1. Запустить dev server.
2. Проверить HMR.
3. Проверить отсутствие ошибок в console.
4. Выполнить typecheck.
5. Выполнить build.
6. Запустить preview и открыть production build.

## Критерий готовности к следующему этапу

Чистый React-каркас успешно работает в dev и production preview.

## Рекомендуемый commit

`Инициализировано React-приложение на Vite`.

# 7. Этап 2. Обязательные пакеты и quality tooling

## Цель

Установить утверждённый стек и настроить единые правила кода до создания большого количества файлов.

## Зависимости

Завершён этап 1.

## Действия

### 7.1. Установить обязательные runtime-зависимости

Установить совместимые версии:

- Mantine Core;
- Mantine Hooks;
- Mantine Notifications;
- Mantine Dates, если дата-поля будут использоваться в первых формах;
- `@tabler/icons-react`;
- `postcss-preset-mantine`;
- `postcss-simple-vars`;
- TanStack Router;
- TanStack Query;
- Motion;
- dayjs.

CSS Modules поддерживаются Vite и не требуют отдельной runtime-библиотеки.

`vite-plugin-pwa` допускается установить на этапе PWA, чтобы не смешивать начальную конфигурацию с service worker.

### 7.2. Не устанавливать условные зависимости

На старте не устанавливать:

- Zod;
- TanStack Form;
- TanStack Table;
- Zustand;
- Redux;
- Axios;
- React Hook Form;
- Mantine Charts;
- i18n;
- test runner;
- Storybook;
- Sentry.

Каждая из этих зависимостей должна появиться только после отдельного решения и понятного use case.

### 7.3. Настроить PostCSS и CSS Modules

1. Создать единый `postcss.config.*`.
2. Подключить `postcss-preset-mantine`.
3. Подключить `postcss-simple-vars`.
4. Подготовить место для PostCSS breakpoint variables, необходимых CSS Modules; окончательные значения синхронизировать с Mantine theme на этапе 4.
5. Проверить, что Vite корректно обрабатывает обычный global CSS и файлы `*.module.css`.
6. Создать минимальный временный CSS Module и проверить локальность class names в development и production build.
7. Не превращать PostCSS variables во вторую независимую систему design tokens.

### 7.4. Настроить ESLint

1. Подключить TypeScript ESLint.
2. Подключить правила React Hooks.
3. Запретить неиспользуемые переменные и очевидные ошибки.
4. Не вводить чрезмерно строгие stylistic rules, которые конфликтуют с Prettier.
5. Исключить generated route tree и build artifacts там, где это необходимо.
6. Не отключать правила локально без объяснимой причины.

### 7.5. Настроить Prettier

1. Добавить единый config.
2. Добавить format и format-check scripts.
3. Настроить игнорирование generated и build-файлов.
4. Убедиться, что ESLint и Prettier не форматируют один и тот же аспект по-разному.

### 7.6. Проверить package hygiene

1. Просмотреть итоговый список dependencies.
2. Удалить случайно установленные шаблонные packages.
3. Проверить lockfile.
4. Не использовать caret/range-решения, противоречащие принятому способу фиксации версий.

## Результат этапа

- установлен минимальный утверждённый стек;
- lint, format, typecheck и build выполняются;
- отсутствуют преждевременные библиотеки;
- PostCSS и CSS Modules корректно обрабатываются Vite;
- Tailwind отсутствует в dependencies и configuration.

## Ручная проверка

- `pnpm lint`;
- `pnpm typecheck`;
- `pnpm format:check`;
- `pnpm build`;
- проверка локальности class names CSS Module в production output;
- просмотр dependency tree на очевидные дубликаты.

## Критерий готовности к следующему этапу

Любой новый код автоматически проходит единые проверки и форматирование.

## Рекомендуемый commit

`Настроен технологический стек frontend`.

# 8. Этап 3. Архитектурный каркас

## Цель

Создать структуру каталогов и правила ownership до появления routes, API и предметного UI.

## Зависимости

Завершён этап 2.

## Действия

### 8.1. Создать основные области

Создать каталоги:

- `src/app`;
- `src/routes`;
- `src/pages`;
- `src/features`;
- `src/shared`.

Создать feature-каталоги:

- `src/features/auth`;
- `src/features/savings`;
- `src/features/purchases`;
- `src/features/profile`.

# 12. Этап 7. Общий API client и TanStack Query

### 12.2. Создать `shared/api`

Минимально предусмотреть:

- общий API client;
- тип нормализованной API-ошибки;
- тип backend error envelope;
- общий тип query parameters при необходимости.

### 12.3. Реализовать обязанности API client

API client должен централизованно обеспечивать:

- base path `/api/v1`;
- Fetch API;
- `credentials: include`;
- `Accept: application/json`;
- `Content-Type: application/json` только для JSON body;
- сериализацию request body;
- обработку query parameters;
- передачу `AbortSignal`;
- корректную обработку `204 No Content`;
- разбор JSON response;
- безопасную обработку пустого или не-JSON error body;
- преобразование backend error envelope в единый `ApiError`;
- сохранение HTTP status, error code, fields и requestId.

API client не должен:

- знать о Purchase или Savings;
- хранить token;
- добавлять Authorization header;
- показывать notifications;
- выполнять route navigation;
- содержать TanStack Query logic;
- валидировать каждый response через Zod.

### 12.4. Зафиксировать архитектуру feature API

Для каждой feature позже создаются чистые функции, например:

- получить список;
- получить одну сущность;
- создать;
- изменить;
- удалить.

Feature API-функция:

- знает endpoint;
- знает request и response TypeScript-типы;
- вызывает общий API client;
- при необходимости разворачивает wrapper `{ items: [...] }`;
- не знает о React-компонентах;
- не показывает UI;
- не управляет cache.

### 12.5. Зафиксировать правила DTO и adapters

1. Описывать backend responses TypeScript-типами.
2. Создавать отдельные create/update input-типы.
3. Не отправлять backend-generated поля.
4. Не создавать DTO/domain/view model для каждой сущности без реальной разницы.
5. Добавлять mapper только на конкретной границе, например form values → request input.
6. Не считать generic API client runtime-валидацией.

### 12.6. Подключить TanStack Query

1. Создать единственный QueryClient.
2. Подключить QueryClientProvider в AppProviders.
3. Настроить разумные defaults:
   - повтор запроса только там, где это безопасно;

   - refetch при восстановлении сети;

4. Подключить Query Devtools только в development и только при необходимости.

- query options создаются рядом с feature API;

# 13. Этап 8. Session-based авторизация

## Цель

Реализовать вход, восстановление session после reload, защищённые маршруты, истечение session и выход.

## Зависимости

Завершены этапы 5–7. Backend auth endpoints доступны.

- login response;

Не добавлять типы access/refresh token.

### 13.2. Создать auth API

Реализовать feature API-функции для:

- login;
- logout;
- current user.

Проверить фактические response shapes backend.

### 13.3. Создать auth query layer

1. Создать стабильный query key для current user.
2. Создать query options для `/me`.
3. Определить поведение `401` как «session отсутствует».
4. Не трактовать network error или 500 как обычный unauthenticated state.
5. Создать login mutation.
6. Создать logout mutation.
7. После успешного login обновить current-user cache либо выполнить refetch.
8. После logout очистить private cache.

### 13.4. Реализовать LoginPage

Форма содержит:

- login;
- password;
- submit.

Требования:

- controlled local state;
- trim login;
- password не trim автоматически;
- блокировка повторного submit;
- pending state;
- понятное сообщение для invalid credentials;
- отдельное сообщение для network/server failure;
- корректные autocomplete attributes;
- отсутствие ручного сохранения credentials;
- сохранение login при ошибке;
- очистка password после успешного входа.

Для двух полей form-библиотека и Zod не нужны.

### 13.5. Включить protected routing

1. Authenticated layout должен дождаться проверки `/me`.
2. Во время первичной проверки показывать нейтральный application loader, а не login flash.
3. При `401` перенаправлять на `/login`.
4. Authenticated пользователя с `/login` перенаправлять на `/`.
5. Сохранять только безопасный внутренний redirect URL.
6. Не разрешать open redirect на внешний адрес.

### 13.6. Обработать истечение session

Выбрать один централизованный механизм:

- общий callback при `401` в query/mutation infrastructure;
- либо auth-session-expired signal, обрабатываемый на app-level.

Требования:

- не дублировать обработку в каждой feature;
- очистить private cache;
- перевести пользователя на login;
- не показывать множество одинаковых notifications;
- не запускать бесконечные refetch loops.

### 13.7. Проверить cache isolation

Так как приложение используют два пользователя:

1. войти первым пользователем;
2. загрузить данные;
3. выйти;
4. войти вторым;
5. убедиться, что UI не показывает cached data первого пользователя до refetch.

## Результат этапа

- приложение корректно восстанавливает session после reload;
- без session доступны только публичные route;
- токены отсутствуют во frontend;
- logout и session expiration безопасно очищают данные.

## Ручная проверка

1. Успешный login.
2. Неверный password.
3. Пустые поля.
4. Прямой переход на `/purchases` без session.
5. Reload защищённой страницы с session.

# 14. Этап 9. Общие primitives для денег, дат и ошибок

## Цель

До финансовых features централизовать небольшие технические правила, которые точно повторятся.

## Зависимости

## Действия

### 14.1. Деньги

Создать shared-функции для:

- форматирования integer minor units в рубли;
- безопасного преобразования пользовательской строки суммы в minor units;
- проверки safe integer;
- обработки пробелов и разделителей;
- отображения нулевой суммы;
- отображения суммы без потери копеек.

Правила:

- вычисления выполняются только в minor units;
- в domain model не хранится formatted string;
- floating point не используется как источник истины;
- преобразование в строку происходит на UI-границе;
- форма может хранить строковое значение, но request получает integer.

### 14.2. Даты

Создать helpers для:

- отображения `YYYY-MM-DD` в русском интерфейсе;
- получения сегодняшней календарной даты;
- определения начала текущего месяца;
- сравнения date-only значений;
- подсчёта календарных месяцев до цели.

Правила:

- date-only строка не должна случайно сдвигаться из-за UTC/timezone;
- timestamps можно преобразовывать через Date/dayjs;
- goal date и entry date обрабатываются как календарные даты;
- логика расчётов принимает текущую дату явно.

### 14.3. API errors

Создать небольшие helpers для:

- получения безопасного пользовательского сообщения;
- определения validation error;
- чтения field errors;
- определения unauthenticated и not-found состояний.

Не показывать raw stack trace или внутренний backend message без проверки.

### 14.4. Form conventions

Зафиксировать общий подход:

- local state;
- client validation перед mutation;
- server field errors после mutation;
- values сохраняются при ошибке;
- optional strings trim и преобразуются в `null`;
- reset выполняется после success или явного cancel;
- submit недоступен во время pending.

Не создавать generic form framework.

## Ручная проверка

- суммы без копеек;

- ноль;
- крупная сумма;
- пробелы в input;
- некорректная строка;
- даты на границе месяца и года;
- backend field error;
- network error.

## Критерий готовности к следующему этапу

Feature-расчёты не должны заново решать вопросы форматирования, minor units и date-only parsing.

2. Суммировать entries до текущего месяца.
3. Рассчитать остаток цели на начало текущего месяца.
4. Посчитать количество календарных месяцев от текущего месяца до месяца цели включительно.
5. Если цель уже достигнута на начало месяца, plan равен нулю.
6. Если месяц цели ещё не прошёл, разделить остаток на число оставшихся месяцев с округлением вверх до minor unit.
7. Если месяц цели прошёл, но цель не достигнута, план текущего месяца равен всему оставшемуся остатку.
8. Суммировать entries текущего месяца.
9. Рассчитать остаток плана и опережение.

### 15.6. Учесть edge cases

- отсутствуют entries;
- цель равна точной сумме entries;
- цель превышена;

- несколько entries в один день;
- entry с датой текущего дня;
- изменение target amount;
- изменение target date;
- очень крупные значения в пределах safe integer.

Savings goal:

- сумма больше нуля;
- сумма преобразуется в safe integer minor units;
- target date корректна;
- политика по прошлой дате соответствует бизнес-требованиям.

Savings entry:

- сумма больше нуля;
- дата корректна;
- будущая дата недопустима в обычном UI;
- comment не превышает backend limit.

### 15.8. Выполнить ручную матрицу расчётов

Так как unit-тесты пока не входят в scope:

1. Подготовить небольшой список входных сценариев и ожидаемых значений.
2. Проверить чистые функции из временного development entry либо console-free dev harness.
3. После проверки удалить временный harness.
4. Не оставлять расчёты только «проверенными глазами» в UI.

# 27. Условия пересмотра стека

## Добавить Zod, если

- client validation стала сложной и повторяется;
- появились cross-field правила;
- несколько форм используют одну схему;
- runtime validation API действительно решает наблюдаемую проблему.

## Добавить TanStack Form, если

- формы существенно выросли;
- появились nested values или arrays;
- ручное управление dirty/reset/field lifecycle стало источником ошибок;
- нужен единый набор field-компонентов.

## Добавить TanStack Table, если

- появился настоящий tabular desktop-screen;
- нужны sorting, selection, pagination, resizing или column management;
- карточный список перестал соответствовать задаче.

## Добавить Zustand, если

- появился глобальный client-only state;
- он не принадлежит Query, Router, Mantine theme или локальному компоненту;
- Context/useState уже создают реальную связанность.

## Добавить Mantine Charts, если

- утверждён конкретный экран аналитики;
- определены метрики и данные;
- график является продуктовым требованием, а не декоративным элементом.
