## 1. Цель и согласованные решения

Получить локально работающее приложение с настоящим backend: вход, накопления, покупки и профиль. Пользователь подтвердил этот вариант первого запуска в чате.

Для этой задачи пользователь включил L7: Codex проектирует, реализует и проверяет frontend целиком. Пользователю не требуется самостоятельно писать production-код этапов. Разрешение относится к текущей задаче; `AGENTS.md` этим документом не изменяется, а режим будущих задач определяется отдельно.

В этом проходе используется простой интерфейс на уже подключённом Mantine: стандартные компоненты, системный шрифт, текущий teal-акцент, светлая и тёмная темы. Собственная дизайн-система и детальная визуальная полировка не являются условием первого запуска.

Две контрольные точки:

1. **Первый полезный запуск:** пользователь входит, задаёт цель, добавляет пополнение и после перезагрузки видит сохранённые данные и обновлённые расчёты.
2. **Локальная рабочая версия:** дополнительно доступны покупки с фильтрами и полным редактированием, профиль и выход.

Установка PWA и публикация по внешней ссылке остаются следующими отдельными этапами. Локальная рабочая версия ещё не означает выполнение всех критериев полного PWA MVP из прежних документов.

## 3. Последовательность реализации

Номера исходных этапов ниже относятся к `05-FRONTEND_EXECUTION_CHECKLIST.md`. Подробные требования сохраняются в документах 01–03; документ 04 используется как справочник. Для текущей L7-задачи приоритеты поставки и границы первого запуска задаёт этот план.

### Этап A. Подтвердить локальное окружение и контракт

Соответствует перепроверке исходных этапов 0–2.

Работы:

- Восстановить запуск закреплённых package managers без несвязанного обновления зависимостей. Frontend использует pnpm 11, backend — pnpm 10; запускать каждый из своего repository.
- Привести форматирование затронутых файлов к пользовательскому Prettier config и получить воспроизводимый baseline проверок.
- Проверить backend environment, PostgreSQL и существующие миграции. Использовать локальную development-БД; существующие данные не сбрасывать.
- Проверить наличие двух учётных записей и способ входа. Запускать seed только при необходимости первоначальной подготовки, учитывая, что он может обновлять пользователей. Секреты не включать в frontend или документацию.
- Проверить `/health`, затем фактические ответы API, DTO, ошибки и session cookie. Наличие исходников backend само по себе не подтверждает успешную интеграцию.

Результат: известен рабочий способ запуска frontend и backend, доступна development-БД и подтверждён способ входа.

Критерий: health подтверждает подключение к БД; package scripts запускаются; расхождения frontend-требований с действующим API выявлены до создания форм.

### Этап B. Собрать оболочку приложения

Соответствует исходным этапам 3–5.

Работы:

- Завершить providers, минимальную Mantine theme, notifications и переключение light/dark с сохранением выбора.
- Подключить TanStack Router и маршруты `/login`, `/`, `/purchases`, `/profile`, а также состояния неизвестного маршрута и неожиданной ошибки.
- Сделать отдельный экран входа и общую оболочку остальных страниц: нижняя навигация на телефоне, верхняя на desktop.
- Собрать простой адаптивный layout со стандартными карточками, кнопками, полями и диалогами Mantine; собственные стили размещать рядом с компонентами в CSS Modules.

Результат: приложение уже можно открыть и оценить навигацию, размеры элементов и обе темы. На этом этапе предметные страницы ещё не считаются рабочими.

Критерий: переходы, back/forward и прямое открытие URL работают; на ширине 320–375 px нет горизонтального переполнения или перекрытого нижней навигацией содержимого.

### Этап C. Подключить API и настоящий вход

Соответствует исходным этапам 6–7.

Работы:

- Настроить Vite proxy и единый API client с относительным `/api/v1`, credentials, отменой запросов и нормализацией ошибок.
- Подключить TanStack Query как владельца серверных данных.
- Реализовать login, восстановление сессии через `/me`, защиту маршрутов и выход.
- Разделить неверный пароль, истёкшую сессию, сетевую ошибку и ошибку сервера; не считать любой сбой `/me` отсутствием авторизации.
- При смене пользователя очищать приватный cache и исключить его повторное заполнение старыми запросами.

Результат: приложение открывает защищённые разделы после настоящего входа, восстанавливает сессию после reload и корректно завершает её.

Критерий: проверены успешный и неуспешный вход, прямой защищённый URL без сессии, reload с сессией, logout, истечение сессии и вход второго пользователя без старых cached данных.

### Этап D. Сделать накопления — первый полезный запуск

Соответствует исходным этапам 8–9.

Работы:

- Реализовать общие правила ввода и отображения денег, date-only дат и ошибок форм.
- Собрать экран цели: сумма, срок, накоплено, остаток, прогресс и план текущего месяца по бизнес-спецификации.
- Добавить создание отсутствующей цели и её редактирование.
- Реализовать историю пополнений, добавление, редактирование и удаление с подтверждением.
- Предусмотреть загрузку, отсутствие записей, ошибки, повторную попытку и pending-состояния; успешное уведомление показывать после подтверждения backend.

Результат: пользователь может вести накопления на настоящих данных.

Критерий: создание и изменение данных переживают reload; суммы пересчитываются после CRUD. Проверены отсутствие цели (`404`), пустая история, достижение и превышение цели, текущий и просроченный месяц, внесение суммы в текущем месяце и изменение пополнения прошлого месяца. Ошибка сохранения оставляет форму доступной для исправления и повтора.

**В этой точке приложение запускается в браузере и демонстрируется пользователю. Работа над покупками не должна задерживать этот показ.**

### Этап E. Добавить покупки и профиль

Соответствует исходным этапам 10–11.

Работы:

- Сделать список покупок, сводку по статусам, фильтры комнат, категорий и статусов.
- Реализовать добавление, редактирование, смену статуса и удаление покупки.
- Учесть нулевую цену, пустые необязательные поля, безопасное открытие внешних HTTP/HTTPS ссылок и русские названия справочников.
- Собрать профиль из уже загруженного `/me`, переключатель темы и выход. Редактирование аккаунта и загрузка аватара не входят в действующий backend-контракт.

Результат: доступны все предметные разделы локальной рабочей версии.

Критерий: CRUD и смена статуса сохраняются после reload; фильтры корректно комбинируются и сбрасываются; сводки соответствуют бизнес-правилам; тема сохраняется; оба пользователя видят общие прикладные данные.

### Этап F. Проверить и передать локальную рабочую версию

Это локальная интеграционная приёмка. Она использует подходящие сценарии исходного этапа 13, но не закрывает его PWA-критерии раньше времени.

Работы:

- Пройти весь путь: вход → цель → пополнение → покупка → смена статуса → reload → выход → вход второго пользователя.
- Проверить мобильный и desktop viewport, обе темы, клавиатуру, фокус в формах и диалогах, состояния загрузки и ошибки сети.
- Запустить `pnpm lint`, `pnpm typecheck`, `pnpm format:check`, `pnpm build`.
- Проверить собранный frontend и прямое открытие вложенных URL. Для проверки API через preview отдельно обеспечить proxy: development proxy сам по себе не является production-инфраструктурой.
- Зафиксировать в repository короткую инструкцию запуска, необходимые переменные без значений секретов, порядок старта сервисов и известные ограничения.
- Передать локальный URL и фактический результат проверок, включая непроверенные сценарии.

Результат: приложение можно воспроизводимо поднять локально и использовать для основных сценариев.

## 4. Контракт и архитектурные ограничения

- Backend хранит исходные данные; расчёты накоплений и сводки покупок выполняет frontend.
- Денежные значения передаются целым числом копеек с суффиксом `Minor`; date-only значения сохраняют формат `YYYY-MM-DD` без сдвига часового пояса.
- Login возвращает `{ user }`, `/me` — объект пользователя напрямую, списки накоплений и покупок — `{ items }`.
- `GET /savings/goal` без созданной цели возвращает `404`, `PUT` создаёт или обновляет цель, удаление и logout возвращают `204` без JSON body.
- Сессия хранится в HttpOnly cookie. Токен не хранится во frontend state или localStorage.
- Auth, формы и прикладной UI не подменяются демо-данными в критериях готовности.
- Сохраняется структура `app / routes / pages / features / shared`; новые библиотеки добавляются только при конкретной необходимости.
- Базовые responsive, доступность и корректные состояния входят в первую версию. Брендинг, сложная анимация и расширенная визуальная система откладываются.

## 5. Проверки и следующие этапы

Текущая техническая спецификация исключает автоматические frontend-тесты из первого прохода. Этот план сохраняет ограничение: обязательны статические проверки и зафиксированные ручные сценарии, особенно для денег, месячного плана и сессии. Пустая тестовая инфраструктура не добавляется; успешный lint или build не заменяет проверку поведения.

После локальной рабочей версии:

1. PWA: manifest, иконки, установка, обновление и offline-состояние без offline mutations и постоянного кеширования приватного API.
2. Полная приёмка PWA MVP по исходному checklist.
3. При необходимости — отдельный план публикации frontend и backend с HTTPS и same-origin API.
4. Визуальная доработка по впечатлениям от уже работающих экранов.

Текущий план A–F завершён. Следующие самостоятельные задачи — PWA, его приёмка и при необходимости публикация. Они не включены в выполненный локальный запуск.
