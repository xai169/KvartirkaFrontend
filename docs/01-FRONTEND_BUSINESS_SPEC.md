# Бизнес-требования к frontend приложения «Квартирка»

## 1. Статус и назначение документа

Документ фиксирует продуктовые требования к frontend PWA-приложения «Квартирка».

Он описывает:

- назначение продукта;
- пользователей и основные сценарии;
- состав MVP;
- поведение экранов;
- правила клиентских финансовых расчётов;
- пользовательские состояния и критерии приёмки.

Связанные документы:

- `BACKEND_SPEC.md` — источник истины для HTTP API, авторизации и форматов данных;
- `02-FRONTEND_ARCHITECTURE.md` — структура frontend-кода и границы модулей;
- `03-FRONTEND_TECHNICAL_SPEC.md` — технологические и нефункциональные требования;
- `04-FRONTEND_IMPLEMENTATION_PLAN.md` — рекомендуемый порядок реализации;
- `05-FRONTEND_EXECUTION_CHECKLIST.md` — компактный рабочий маршрут от инициализации до приёмки MVP.

При расхождении с backend-контрактом frontend должен быть приведён в соответствие с `BACKEND_SPEC.md`. План реализации не является источником продуктовых требований.

---

## 2. Цель продукта

«Квартирка» — приватное приложение для двух заранее известных пользователей, которые совместно:

- накапливают деньги к заданной дате;
- видят общий прогресс достижения финансовой цели;
- понимают, сколько нужно внести в текущем месяце;
- ведут историю пополнений;
- планируют покупки для квартиры;
- распределяют покупки по комнатам и категориям;
- меняют статус покупок от идеи до завершения;
- контролируют общий объём запланированных покупок.

Приложение не является банковским сервисом, бухгалтерской системой или публичным каталогом товаров. Оно хранит введённые пользователями факты и помогает визуально интерпретировать их.

---

## 3. Пользователи и модель доступа

### 3.1. Пользователи

В системе существуют два заранее созданных аккаунта.

Публичная регистрация отсутствует.

### 3.2. Общая область данных

Оба пользователя имеют одинаковый доступ ко всем прикладным данным:

- общей цели накопления;
- всем записям пополнений;
- всем покупкам.

Данные не делятся на личные и общие.

### 3.3. Роли и права

В MVP отсутствуют:

- роли;
- разграничение прав;
- администратор;
- владелец записи;
- запрет редактирования чужих записей.

Оба пользователя могут создавать, изменять и удалять общие данные.

---

## 4. Основные продуктовые принципы

1. **Mobile first.** Главный сценарий — использование со смартфона.
2. **Минимум действий.** Добавление пополнения или покупки не должно требовать перехода через несколько экранов.
3. **Один источник истины.** Backend хранит исходные данные, frontend рассчитывает производные значения.
4. **Производные данные не редактируются вручную.** Пользователь изменяет цель, пополнения и покупки, а суммы и проценты пересчитываются автоматически.
5. **Простой MVP.** Не добавлять функции, которые не нужны двум реальным пользователям сейчас.
6. **Современная визуальная подача.** Интерфейс должен напоминать по качеству и ритму современные банковские приложения, но не копировать конкретный продукт.
7. **Русскоязычный интерфейс.** Международная локализация и переключение языка в MVP отсутствуют.

- `/login` — авторизация.

### 5.2. Защищённые разделы

- `/` — накопления;

На широком экране допускается перенос этих пунктов в верхнюю навигацию, при этом состав и смысл маршрутов не меняются.

# 6. Авторизация

## 6.1. Экран входа

Форма содержит:

- логин;
- пароль;
- кнопку «Войти».

### 6.2. Поведение

При успешном входе:

1. backend устанавливает HttpOnly session cookie;
2. frontend считает пользователя авторизованным;
3. пользователь переходит на главную страницу либо на ранее запрошенный защищённый маршрут.

При неверных данных показывается единое сообщение:

> Неверный логин или пароль

Нельзя сообщать, существует ли конкретный логин.

### 6.3. Уже активная сессия

Если авторизованный пользователь открывает `/login`, он перенаправляется на главную страницу.

### 6.4. Истёкшая сессия

Если любой защищённый запрос возвращает `401`:

- локальное представление авторизации сбрасывается;
- защищённый интерфейс больше не показывается;
- пользователь перенаправляется на `/login`;
- после повторного входа допускается возврат на исходный маршрут.

### 6.5. Выход

Кнопка «Выйти» находится на странице профиля.

После успешного logout:

- пользовательские серверные данные удаляются из frontend-кеша;
- пользователь перенаправляется на `/login`;
- защищённые страницы становятся недоступны.

# 7. Раздел «Накопления»

## 7.1. Назначение

Главный экран должен за несколько секунд отвечать на вопросы:

- сколько уже накоплено;
- какова общая цель;
- сколько осталось;
- какой процент цели выполнен;
- сколько требуется внести в текущем месяце;
- сколько уже внесено в этом месяце;
- какие пополнения были добавлены ранее.

## 7.2. Исходные данные

Frontend получает:

- одну общую `SavingsGoal`;
- список `SavingsEntry[]`.

Backend не возвращает готовую сводку. Все значения ниже рассчитываются на frontend.

## 7.3. Главная карточка цели

Карточка показывает:

- целевую сумму;
- накопленную сумму;
- остаток до цели;
- процент выполнения;
- дату достижения цели;
- визуальный progress indicator.

Пример содержания:

```text
Накоплено
850 000 ₽ из 1 500 000 ₽
57%
Осталось 650 000 ₽
Цель до 30 июня 2027 года
```

Если накоплено больше цели:

- progress indicator визуально ограничивается 100%;
- отдельно может показываться превышение цели;
- сумма накоплений не должна искусственно обрезаться до целевой.

## 7.4. Базовые расчёты цели

Пусть:

- `targetAmountMinor` — целевая сумма;
- `entries` — все записи пополнений;
- `savedAmountMinor` — сумма `amountMinor` всех записей.

Frontend рассчитывает:

```text
savedAmountMinor = сумма всех entries.amountMinor
remainingAmountMinor = max(targetAmountMinor - savedAmountMinor, 0)
overTargetAmountMinor = max(savedAmountMinor - targetAmountMinor, 0)
rawProgressPercent = savedAmountMinor / targetAmountMinor * 100
displayedProgressPercent = min(rawProgressPercent, 100)
```

Денежные вычисления выполняются в целых копейках.

## 7.5. Статус срока

Цель имеет один из состояний:

- `active` — срок ещё не наступил и цель не достигнута;
- `completed` — накопленная сумма равна цели или превышает её;
- `overdue` — срок прошёл, но цель не достигнута.

Если цель достигнута, состояние `completed` имеет приоритет над `overdue`.

## 7.6. План текущего месяца

Месячный план рассчитывается так, чтобы:

- текущий месяц имел стабильную цель после его начала;
- внесённые в текущем месяце деньги уменьшали именно остаток текущего месяца;
- недобор или превышение автоматически учитывались при расчёте следующих месяцев;
- изменение исторической записи корректно пересчитывало план.

### 7.6.1. Определения

- `monthStart` — первый календарный день текущего месяца;
- `savedBeforeCurrentMonthMinor` — сумма записей с датой раньше `monthStart`;
- `savedCurrentMonthMinor` — сумма записей текущего календарного месяца;
- `remainingAtMonthStartMinor` — остаток цели на начало месяца;
- `monthsToTargetInclusive` — количество календарных месяцев от текущего месяца до месяца цели включительно.

```text
remainingAtMonthStartMinor =
    max(targetAmountMinor - savedBeforeCurrentMonthMinor, 0)
```

Например, если сейчас август, а цель установлена на июнь следующего года, учитываются август и июнь, а также все месяцы между ними.

### 7.6.2. Требуемая сумма месяца

Если цель уже была достигнута к началу месяца:

```text
requiredCurrentMonthMinor = 0
```

Если месяц цели ещё не прошёл:

```text
requiredCurrentMonthMinor =
    ceil(remainingAtMonthStartMinor / monthsToTargetInclusive)
```

Если месяц цели уже прошёл, но цель не достигнута:

```text
requiredCurrentMonthMinor = remainingAtMonthStartMinor
```

Округление выполняется вверх до одной копейки, чтобы сумма месячных планов не оказалась меньше цели.

### 7.6.3. Выполнение плана месяца

```text
currentMonthRemainingMinor =
    max(requiredCurrentMonthMinor - savedCurrentMonthMinor, 0)

currentMonthAheadMinor =
    max(savedCurrentMonthMinor - requiredCurrentMonthMinor, 0)
```

Экран показывает:

- план текущего месяца;
- внесено в текущем месяце;
- осталось внести;
- при превышении — сумму опережения.

### 7.6.4. Пересчёт

Расчёт выполняется заново при изменении:

- цели;
- списка пополнений;
- текущего календарного месяца.

Производные значения не сохраняются ни в backend, ни в отдельном frontend-state.

## 7.7. Изменение цели

Пользователь может открыть настройки цели и изменить:

- целевую сумму;
- целевую дату.

После сохранения все производные значения пересчитываются автоматически.

Если `GET /savings/goal` возвращает отсутствие цели, frontend показывает первичную настройку цели вместо обычного дашборда. Основной ожидаемый сценарий — цель создана backend seed-скриптом.

## 7.8. Добавление пополнения

Форма содержит:

- сумму — обязательное поле;
- дату — обязательное поле, по умолчанию сегодня;
- комментарий — необязательное поле.

После успешного создания:

- форма закрывается;
- история обновляется;
- все показатели пересчитываются;
- показывается уведомление об успехе.

Дата будущего дня не должна предлагаться в обычном UI.

## 7.9. История пополнений

Записи отображаются от новых к старым.

Для каждой записи показываются:

- сумма;
- дата;
- комментарий при наличии;
- меню действий.

Автор записи в MVP не показывается, так как API возвращает только `createdByUserId`, но не публичные данные второго пользователя.

## 7.10. Редактирование и удаление пополнения

Пользователь может:

- изменить сумму, дату или комментарий;
- удалить запись после подтверждения.

После изменения или удаления сводка должна пересчитаться из актуального списка записей.

## 7.11. Пустое состояние

Если записей ещё нет, показывается:

- пояснение, что пополнений пока нет;
- заметная кнопка «Добавить накопление»;
- нулевой прогресс цели.

# 8. Раздел «Покупки»

## 8.1. Назначение

Раздел должен отвечать на вопросы:

- что планируется купить;
- для какой комнаты нужна покупка;
- к какой категории она относится;
- сколько она стоит;
- где её можно заказать;
- каков её текущий статус;
- какова общая сумма списка.

## 8.2. Комнаты

Используются фиксированные значения:

| Значение API | Название в интерфейсе |
|---|---|
| `kitchen` | Кухня |
| `bedroom` | Спальня |
| `living-room` | Гостиная |
| `bathroom` | Ванная |
| `hallway` | Прихожая |
| `common` | Общие |

«Общие» используются для покупок, не относящихся к одной комнате.

Пользователь не может создавать или переименовывать комнаты в MVP.

## 8.3. Категории

| Значение API | Название в интерфейсе |
|---|---|
| `furniture` | Мебель |
| `appliances` | Техника |
| `lighting` | Освещение |
| `plumbing` | Сантехника |
| `textile` | Текстиль |
| `tableware` | Посуда |
| `decor` | Декор |
| `tools` | Инструменты |
| `other` | Другое |

Пользователь не может создавать собственные категории в MVP.

## 8.4. Статусы

| Значение API | Название | Смысл |
|---|---|---|
| `planned` | Запланировано | Покупка добавлена в план, заказ не оформлен |
| `ordered` | Заказано | Заказ оформлен, но покупка ещё не завершена |
| `purchased` | Куплено | Покупка завершена |

Дополнительные статусы в MVP отсутствуют.

## 8.5. Карточка покупки

Карточка должна показывать:

- название;
- цену либо «Цена не указана»;
- комнату;
- категорию;
- статус;
- магазин при наличии;
- ссылку на товар при наличии;
- меню редактирования и удаления.

Комментарий может показываться в раскрытом состоянии или в форме редактирования, чтобы не перегружать список.

## 8.6. Цена

Поле `priceMinor` обязательно в API и допускает значение `0`.

В MVP значение `0` интерпретируется как:

> Цена пока не указана

Такая покупка участвует в количестве элементов, но не увеличивает финансовые суммы. Интерфейс должен отдельно показывать количество покупок без указанной цены, если оно больше нуля.

## 8.7. Добавление покупки

Форма содержит:

- название — обязательное;
- цену — допускается оставить нулевой;
- комнату — обязательное;
- категорию — обязательное;
- статус — обязательное, по умолчанию `planned`;
- магазин — необязательное;
- ссылку — необязательное;
- комментарий — необязательное.

После успешного создания:

- форма закрывается;
- список и финансовая сводка обновляются;
- показывается уведомление.

## 8.8. Редактирование покупки

Пользователь может изменить любое редактируемое поле покупки.

Быстрое изменение статуса может выполняться непосредственно из карточки, если это не ухудшает мобильный UX.

## 8.9. Удаление покупки

Удаление требует подтверждения.

После удаления список, количества и суммы пересчитываются.

## 8.10. Фильтрация

На MVP обязательна фильтрация по комнате.

Также интерфейс должен быть подготовлен к фильтрации по:

- статусу;
- категории.

Фильтрация выполняется на frontend по уже загруженному списку. Backend-фильтры остаются доступным контрактом, но не обязательны для первого варианта UI.

Активные фильтры желательно хранить в search-параметрах URL, чтобы состояние сохранялось при обновлении страницы и могло быть воспроизведено по ссылке.

## 8.11. Порядок отображения

Если пользователь не выбрал другую сортировку, покупки отображаются:

1. `planned`;
2. `ordered`;
3. `purchased`;
4. внутри одного статуса — по `updatedAt` от новых к старым.

Пользовательская настройка сортировки в MVP не требуется.

## 8.12. Финансовая сводка покупок

Frontend рассчитывает:

```text
totalAmountMinor = сумма priceMinor всех покупок
plannedAmountMinor = сумма покупок со статусом planned
orderedAmountMinor = сумма покупок со статусом ordered
purchasedAmountMinor = сумма покупок со статусом purchased
activeAmountMinor = plannedAmountMinor + orderedAmountMinor
unknownPriceCount = количество покупок с priceMinor = 0
```

`activeAmountMinor` означает стоимость незавершённых позиций, а не гарантированный остаток будущих расходов: заказанный товар уже мог быть оплачен. Поэтому в интерфейсе следует использовать формулировки:

- «Запланировано»;
- «Заказано»;
- «Куплено»;
- «Незавершённые покупки».

Не использовать формулировку «точно осталось потратить», пока в модели нет отдельного признака оплаты.

## 8.13. Группировки

Frontend может рассчитывать группы:

- по комнате;
- по категории;
- по статусу.

В MVP основным способом навигации остаётся выбор комнаты.

## 8.14. Пустые состояния

Нужно различать:

- покупок нет вообще;
- покупки есть, но текущий фильтр ничего не нашёл.

В первом случае показывается кнопка создания покупки. Во втором — действие сброса фильтров.

# 9. Раздел «Профиль»

## 9.1. Данные пользователя

Страница показывает данные `GET /me`:

- username;
- login.

Поля доступны только для просмотра.

## 9.2. Тема

Пользователь может выбрать одну из двух тем:

- светлую;
- тёмную.

Выбор сохраняется локально в браузере и применяется при следующем запуске.

Backend не хранит тему.

## 9.3. Выход

На странице находится кнопка logout.

## 9.4. Что не входит в профиль MVP

Не реализуются:

- изменение username;
- изменение login;
- аватар;
- загрузка файлов;
- изменение пароля;
- восстановление пароля;
- управление другими сессиями.

# 10. Темы и визуальный стиль

## 10.1. Цветовые схемы

Приложение поддерживает ровно две пользовательские схемы:

- light;
- dark.

Все основные экраны, состояния и компоненты должны быть пригодны для обеих тем.

## 10.2. Визуальный характер

Интерфейс должен использовать:

- крупные финансовые значения;
- ясную визуальную иерархию;
- карточки с достаточным воздухом;
- современные tabs и segmented controls;
- спокойные анимации;
- минимальное количество декоративного шума;
- понятные цветовые статусы.

Дизайн не должен буквально копировать интерфейс конкретного банка.

## 10.3. Цвет как дополнительный сигнал

Смысл состояния нельзя передавать только цветом. Статус покупки должен иметь текстовую подпись, а ошибки — поясняющий текст.

---

# 11. Состояния загрузки и ошибок

Каждый экран, зависящий от API, должен иметь:

- состояние первоначальной загрузки;
- состояние успешной загрузки;
- пустое состояние;
- состояние ошибки;
- возможность повторить запрос.

Для первоначальной загрузки предпочтительны skeleton-компоненты, соответствующие будущей разметке.

При мутации:

- кнопка отправки блокируется;
- повторная отправка той же операции предотвращается;
- пользователь видит progress;
- форма остаётся открытой при ошибке;
- введённые данные не теряются.

---

# 12. Уведомления и подтверждения

Успешные операции могут сопровождаться короткими notifications:

- «Накопление добавлено»;
- «Запись изменена»;
- «Покупка добавлена»;
- «Статус обновлён».

Удаление всегда требует подтверждения.

Технические тексты backend не должны напрямую показываться пользователю, если они не являются безопасным и понятным пользовательским сообщением.

---

# 13. PWA-поведение

Приложение должно устанавливаться на домашний экран как PWA.

В MVP требуется:

- manifest;
- иконки;
- standalone-режим;
- кеширование app shell и статических ресурсов;
- корректный запуск по прямым ссылкам на маршруты.

Не требуется:

- создание и изменение данных без сети;
- очередь offline-операций;
- разрешение конфликтов синхронизации;
- push-уведомления.

Если сеть отсутствует, пользователь должен увидеть понятное сообщение, а не бесконечную загрузку.

---

# 14. Responsive-поведение

## 14.1. Мобильный приоритет

На маленьких экранах:

- основная навигация фиксируется снизу;
- формы открываются в удобном для touch-ввода Drawer/Modal;
- интерактивные зоны имеют достаточный размер;
- горизонтальный скролл страницы не допускается;
- ключевые суммы видны без лишних переходов.

## 14.2. Планшет и desktop

На широких экранах:

- контент ограничивается разумной максимальной шириной;
- карточки могут располагаться в несколько колонок;
- навигация может переходить в верхнюю панель;
- мобильная функциональность полностью сохраняется.

Отдельное desktop-приложение в MVP не проектируется.

---

# 15. Доступность

Минимальные требования:

- все поля имеют видимые labels;
- элементы доступны с клавиатуры;
- focus state не скрывается;
- иконки без текста имеют доступное имя;
- модальные окна удерживают и возвращают focus;
- контраст текста и фона достаточен в обеих темах;
- анимации учитывают `prefers-reduced-motion`;
- интерактивные зоны на мобильном ориентированы минимум на комфортный touch-размер.

---

# 16. Что не входит в MVP

Не реализуются:

- публичная регистрация;
- роли и разрешения;
- отдельные пространства/семьи/проекты;
- редактирование профиля;
- аватары и загрузка изображений;
- изображения товаров;
- пользовательские комнаты и категории;
- поиск;
- pagination;
- сложные таблицы;
- отдельный экран аналитики;
- графики;
- сравнение цен;
- история изменения стоимости;
- несколько ссылок на один товар;
- уведомления по расписанию;
- push;
- offline mutations;
- WebSocket-синхронизация;
- импорт и экспорт данных;
- мультиязычность.

---

# 17. Возможности после MVP

После отдельного продуктового решения могут быть добавлены:

- графики накоплений;
- аналитика по комнатам и категориям;
- поиск и расширенная сортировка;
- собственные комнаты и категории;
- изображения покупок;
- редактирование профиля и аватар;
- несколько финансовых целей;
- приоритет покупки;
- история цены;
- синхронизация между открытыми клиентами в реальном времени;
- offline-first режим;
- push-уведомления.

Эти возможности не должны заранее усложнять MVP-архитектуру.

---

# 18. Критерии бизнес-приёмки MVP

MVP считается соответствующим бизнес-требованиям, если:

1. Один из двух существующих пользователей может войти по логину и паролю.
2. Неавторизованный пользователь не видит защищённые страницы.
3. Пользователь видит общую цель, накопленную сумму, остаток, процент и срок.
4. Месячный план рассчитывается по правилам этого документа.
5. Пользователь может создать, изменить и удалить пополнение.
6. После каждой операции показатели накоплений пересчитываются без ручного обновления страницы.
7. Пользователь может изменить сумму и дату общей цели.
8. Пользователь видит список покупок и финансовую сводку.
9. Пользователь может создать, изменить, удалить покупку и поменять её статус.
10. Покупки можно отфильтровать по комнате.
11. Комнаты, категории и статусы отображаются русскими названиями.
12. Профиль показывает login и username.
13. Пользователь может переключить светлую и тёмную темы, а выбор сохраняется.
14. Logout завершает сессию и возвращает на экран входа.
15. Интерфейс полноценно работает на смартфоне и не ломается на desktop.
16. Приложение можно установить как PWA.
17. При загрузках, пустых данных и ошибках пользователь получает понятное состояние.
