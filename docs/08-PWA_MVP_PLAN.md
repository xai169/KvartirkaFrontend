# План PWA и приёмки MVP

Дата: 24 октября 2026 года. Режим: L7, Ponytail full.
Целевая платформа: iPhone 17, iOS 26.6.2, Safari и приложение с домашнего экрана.

## 1. Уточнение объёма задачи

После создания goal пользователь уточнил: реализовать PWA, не готовить QA/HTTPS-стенд и не автоматизировать браузерную приёмку. Пользователь сам проверит iPhone по пошаговому чек-листу. Это решение заменяет первоначальное условие, по которому Codex должен был дождаться доказанной приёмки устройства.

Текущий результат: PWA реализовано; статические проверки и просмотр сборки выполняет Codex, ручные сценарии переданы пользователю в [отчёте и чек-листе](09-PWA_MVP_VERIFICATION.md). Полная runtime-приёмка не объявляется пройденной до результатов пользователя.

Документ продолжает этапы 12–13 [основного checklist](05-FRONTEND_EXECUTION_CHECKLIST.md). [Приёмка 16 октября](07-LOCAL_MVP_VERIFICATION.md) остаётся историческим отчётом локальной версии и не подтверждает новую PWA-функциональность.

## 2. Цель и условия завершения работы Codex

Реализовать устанавливаемую «Квартирку» с кешированием публичной оболочки, понятным offline-состоянием и управляемым обновлением, сохранив существующие бизнес-функции.

Работа Codex завершена, когда:

- production build содержит manifest, service worker и иконки, включая Apple touch icon;
- приватные API-ответы и изменяющие запросы не попадают в PWA-кеш;
- предусмотрено обновление с подтверждением, защитой текущих mutations и открытых вкладок;
- сохраняется работа обычной браузерной версии;
- lint, typecheck, format check и build проходят;
- просмотрены исходные изменения и сгенерированный SW;
- написан понятный ручной чек-лист для iPhone 17 / iOS 26.6.2;
- документы ясно отделяют выполненные проверки от непроверенного runtime-поведения.

За границами: браузерная автоматизация, инфраструктура QA, настройка HTTPS, публичный deployment, изменение основных аккаунтов/данных, offline-редактирование, очереди mutations, push, realtime, редизайн и новые бизнес-функции.

Устройство и цикл обновления A → B проверяет пользователь. Отсутствие этих результатов не блокирует передачу уточнённой задачи Codex, но не позволяет назвать полную PWA-приёмку успешной.

## 3. Goal и разрешения

Goal создана по явной просьбе пользователя. Актуальные границы определяются этим документом и последующим уточнением в чате. L7 разрешён пользователем для этого чата; Ponytail full задаёт минимальный полноценный способ реализации.

Текст цели для воспроизведения уточнённого запроса:

> Реализуй PWA «Квартирки» по docs/08-PWA_MVP_PLAN.md в L7 с Ponytail full для iPhone 17 / iOS 26.6.2. Сохрани бизнес-правила и данные, кешируй только публичную оболочку, исключи offline mutations и неожиданную потерю формы при обновлении. Выполни статические проверки и подготовь пошаговый ручной чек-лист. Не создавай QA/HTTPS-инфраструктуру и автоматические браузерные тесты: приёмку iPhone и обновления я выполню самостоятельно. Заверши по разделу 2, явно указав непроверенные сценарии.

Goal закрепляет цель между сообщениями; само упоминание goal не включает её и не меняет уровень помощи. [Описание Goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex), [команды Codex](https://learn.chatgpt.com/docs/developer-commands).

## 4. Исходное состояние и инварианты

До изменения PWA отсутствовало. Использовались Node.js 24, pnpm 10.34.5, Vite 8.2.2, React 19. Исходные lint, typecheck, форматирование и сборка прошли. Существующий API использует относительный /api/v1, HttpOnly cookie и HTTP cache: no-store; mutations не повторяются автоматически и не ставятся в offline-очередь.

Сохраняемые правила:

1. Backend владеет данными и сессиями. Финансовые расчёты не меняются.
2. Service worker хранит публичные ресурсы; auth, /me, savings и purchases остаются сетевыми.
3. Query cache в памяти, HTTP-кеш и Cache Storage — разные механизмы. no-store у fetch не заменяет настройки SW.
4. Отсутствие ответа API не считается успешным сохранением и не равно 401.
5. При ошибке сохранения форма остаётся открытой. Восстановление сети не отправляет её автоматически.
6. Перезагрузка для обновления требует осознанного действия; pending-mutation не прерывается.
7. Открытая форма другой вкладки не должна теряться из-за обновления текущей.
8. Offline-запуск оболочки предполагает предварительный онлайн-запуск и подготовленный кеш. Доступ к приватным данным без сети не обещается.
9. Реальные аккаунты и прикладные данные не меняются ради приёмки.

Если backend сохранил запись, а ответ потерялся, ручной повтор может создать дубль. Перед повтором нужно сверить данные; backend-idempotency не добавляется в эту задачу.

## 5. Этапы

### A. Baseline и зависимости

Проверить Git status, конфигурацию, доступные версии и peer dependencies. Подключить только стабильные совместимые PWA-зависимости, не менять остальные прямые версии.

Результат: vite-plugin-pwa 2.0.0 и workbox-window 7.4.1; Node/Vite совместимы. Тестовый framework не остаётся в зависимостях.

### B. Manifest и иконки

Настроить название «Квартирка», русский язык, стартовый маршрут /, область /, standalone и базовые цвета. Подготовить обычные иконки 192/512, maskable, Apple touch icon 180 и favicon.

Результат: описание приложения и ресурсы входят в production build. Качество основной иконки и размеры PNG проверены локально; отображение домашнего экрана проверит пользователь.

### C. Кеш оболочки

Использовать generateSW из PWA-плагина. Включить HTML, JS/CSS, необходимые chunks маршрутов и иконки. Исключить API, файлы и assets из навигационного fallback. Не добавлять runtime-кеш API.

Результат: готовая сборка содержит статический precache и SPA fallback только для UI-навигации. PWA не регистрируется обычным dev server.

### D. Сеть и запуск без связи

Сохранить существующие NetworkStatus, обработку ошибок и формы. Проверить по коду границы: cold offline launch может показать оболочку с ошибкой загрузки, данные в памяти открытого приложения не становятся постоянной offline-копией.

Результат: добавленный SW не подменяет авторизацию, API и mutations. Фактическое поведение без сети проверяется по ручному чек-листу.

navigator.onLine — подсказка о подключении, а не доказательство доступности backend. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine).

### E. Управляемое обновление

Использовать стандартную регистрацию плагина с собственным подтверждением перезагрузки. Показывать «Обновить» и «Позже». Не активировать принудительно ожидающую версию, пока открыты другие клиенты того же origin.

Минимальное дополнение к сгенерированному SW — обработчик сообщения, проверяющий количество окон перед skipWaiting. Это позволяет обойтись без протокола синхронизации состояния форм между вкладками. Во время сохранения кнопки обновления недоступны.

Проверять наличие новой версии при foreground, восстановлении связи и раз в час в видимом окне. Ошибка фоновой проверки не мешает текущей версии. При ошибке регистрации объяснить, что offline-оболочка не подготовлена.

Результат: добавлены компонент PwaUpdates и небольшой SW-обработчик. Реальный цикл A → B остаётся ручным сценарием.

### F. Совместимость с iPhone

Сохранить viewport-fit, добавить верхние/боковые safe-area отступы, сохранить нижние отступы навигации. Подготовить Apple touch icon и установку в standalone.

Результат: код ориентирован на iPhone 17 / iOS 26.6.2. Физическое устройство, клавиатура и lifecycle iOS не эмулируются и не объявляются проверенными.

### G. Статические проверки и обзор

Выполнить ESLint, TypeScript build check, Prettier check и production build. Просмотреть manifest, generated SW, API-исключения, изменённые исходники, lock-файл и Git diff. Убедиться, что нет лишних зависимостей и изменений бизнес-логики.

Результат: воспроизводимая сборка и зафиксированные статические проверки. Автоматические браузерные тесты не создаются по просьбе пользователя.

### H. Передача ручной приёмки

Обновить README, checklist и [отчёт 09](09-PWA_MVP_VERIFICATION.md). Дать действия «что нажать» для установки, перезапуска, тем, форм, сети, обновления и нескольких вкладок. Для каждого сценария указать ожидаемый результат.

Результат: пользователь может самостоятельно проверить устройство и сообщить конкретный неуспешный шаг. Не требовать ответа пользователя для завершения уже согласованной реализации.

## 6. Требования к будущей ручной среде

Для PWA на iPhone нужна production-сборка по HTTPS с доступным same-origin API. http://192.168… подходит для просмотра интерфейса, но не полноценной проверки SW. localhost — исключение только на том устройстве, где открыт браузер. HTTPS-стенд в этой задаче не поднимается. [MDN: требования установки](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

Сервер должен корректно отдавать UI fallback, отдельно проксировать /api/v1 и не отдавать index.html вместо отсутствующего SW/JS/CSS. SW, manifest и HTML должны перепроверяться без длительного immutable-кеширования.

Для проверки обновления нужны две отличающиеся сборки на одном origin. Для проверки нескольких клиентов — две вкладки одного browser-контекста. Safari и установленное приложение не обязаны постоянно разделять всё хранилище. [WebKit: login cookies](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/).

Наличие иконки на домашнем экране недостаточно для подтверждения всей PWA-функциональности. Современная iOS позволяет добавлять сайты как веб-приложения независимо от полноты нашей реализации. [WebKit: web apps](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/).

## 7. Понятия

| Понятие | Значение |
|---|---|
| Goal | Постоянная цель чата с критериями завершения; создана по просьбе пользователя |
| L7 | Разрешение Codex самостоятельно реализовать и проверить решение |
| Ponytail full | Минимальное полноценное решение без лишних функций и абстракций |
| PWA | Веб-приложение с установкой и интеграцией с устройством |
| Manifest | Имя, иконки, область и параметры запуска |
| Standalone | Окно приложения без обычной панели браузера |
| Service worker | Отдельный browser worker для сетевых событий и кеширования |
| App shell | Публичные HTML, JS, CSS и ресурсы запуска UI; не приватные данные |
| Precache / Cache Storage | Предварительное сохранение ресурсов / хранилище ответов для SW |
| Query cache | Данные TanStack Query в памяти; не offline-база |
| Mutation | Создание, изменение или удаление данных через API |
| Online-first | Для основной работы с данными нужен API |
| Origin / scope | Адресная граница сайта / область приложения или SW |
| SW lifecycle | Установка, ожидание и активация worker |
| Safe area | Отступы от вырезов и системных элементов экрана |
| Регрессия | Проверка, что существующие функции продолжают работать |

Словарь не является Learning Review и не означает, что у пользователя обнаружены пробелы.

Технические источники: [Vite PWA](https://vite-pwa-org.netlify.app/guide/), [обновления](https://vite-pwa-org.netlify.app/guide/prompt-for-update), [Workbox Routing](https://developer.chrome.com/docs/workbox/modules/workbox-routing).
